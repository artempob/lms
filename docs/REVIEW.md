# Состояние LMS после исправлений

Проверка: 26 ноября 2026 года. Обновляет первоначальный разбор от 19 ноября. Часть исправлений автор выполнил поэтапно сам, оставшаяся работа объединяет их в работающий сценарий.

## Результат

Теперь связана цепочка: регистрация → кошелёк → создание курса учителем → добавление урока → публикация → покупка учеником → чтение → завершение → сохранённый прогресс. Каталог и персональные данные загружаются из API. Учебные подстановки баланса, списка курсов и случайного прогресса удалены.

Успешно выполнены `npm run build` и `mvnw.cmd -B -Ptest-db clean verify`: 21 тест без ошибок. В браузере на отдельной БД проверены платная покупка с уменьшением баланса, прогресс после обновления, авторский предпросмотр, регистрация и отсутствие чужих данных после смены аккаунта. Это подтверждает эти сценарии, но не является полным аудитом безопасности или нагрузочным тестированием.

## Исправленные области

| Область | Текущее поведение |
| --- | --- |
| Авторизация | Один типизированный `JwtPrincipal`, реальные UUID из токена, проверки ролей и владельца |
| Видимость курса | Опубликованный доступен публично, черновик и архивный — автору |
| Авторский интерфейс | Собственные материалы, создание курса, добавление текста/видеоссылки, публикация и предпросмотр |
| Покупка | Один `PurchaseService`, блокировка кошелька, проверка повторов/средств/статуса, списание + журнал + доступ в одной транзакции |
| Уроки | Реальные GET урока/программы, проверка покупки или авторства и принадлежности урока курсу |
| Прогресс | Повторное завершение безопасно, конкурентное завершение сериализуется, счётчики берутся из БД |
| Ошибки | 400/401/403/404/409 по смыслу, неожиданный 500 с `requestId`, подробности только в серверном логе |
| Состояние frontend | Один auth store, серверные данные в Query cache, приватные ключи с ID пользователя, очистка при смене сессии |
| Сборка | Миграции до jOOQ, рабочая чистая сборка, отдельная тестовая PostgreSQL, ленивые страницы и подключённый Tailwind |
| Границы модулей | Публичные контракты вместо импорта `users.internal`, проверка Modulith проходит; генерируемый jOOQ исключён как инфраструктура |
| Схема | Сохранены V1–V7; V8 добавляет ограничения денег, порядка уроков и внешний ключ прогресса |

## Плюсы и цена решений

| Решение | Что даёт | Ограничение |
| --- | --- | --- |
| Модульный монолит | Одна поставка и БД, явные предметные области, проще довести продукт до рабочего состояния | Правила модулей не контролируют, кто читает какую SQL-таблицу; покупка пока имеет доступ к нескольким областям |
| JPA + jOOQ | Удобные агрегаты для команд, явный SQL для чтения и атомарной покупки | Два способа доступа к данным, необходимость генератора; нельзя рассчитывать, что JPA всегда уже отправила изменения в БД |
| `FOR UPDATE` | Последовательная работа запросов с одним кошельком, курсом или записью ученика | Запрос может ждать блокировку; порядок захвата важен для предотвращения взаимных блокировок |
| Ограничения БД | Защищают данные даже при обходе HTTP-валидации | Не описывают всю бизнес-политику; ошибку SQL нельзя автоматически считать ошибкой пользователя |
| События для проекций | Пользователи и курсы не знают, кто создаёт кошелёк и копию цены | Обработка после commit может задерживаться, повторяться или требовать восстановления после сбоя |
| Query cache | Согласованные баланс, покупки и прогресс после изменений | Нужно правильно выбирать ключи и инвалидировать связанные запросы |
| URL урока | Обновление страницы и прямая ссылка сохраняют выбор урока | При неверном/чужом ID сервер обязан отказать; один маршрут не является проверкой прав |
| Один репозиторий | Контракты frontend/backend меняются вместе | Общий `src` непривычен; перенос в `frontend/` и `backend/` полезен позже отдельным изменением |

## Важные оставшиеся решения

1. **Архивный оплаченный курс.** Сейчас ученик не читает непубличный курс даже с ACTIVE-записью. Нужно определить продуктовую политику до добавления архивации. Не менять её случайно одновременно с рефакторингом.
2. **Финансовый журнал.** Покупки пишут WITHDRAWAL, но начальные и вручную изменённые балансы не восстановлены в историю. Сумма текущих транзакций не обязана объяснять старый баланс. Для настоящих денег нужны отдельный сценарий пополнения, проверенные уведомления платёжного провайдера и идемпотентность внешних операций.
3. **Структурированная связь списания и покупки.** Сейчас course UUID есть только в описании журнала. Нужна отдельная колонка/ссылка на покупку и миграция, если планируются возвраты и отчёты.
4. **Границы сценария покупки.** Выбрать владельца процесса и публичные синхронные API модулей, сохранив одну транзакцию. Превращение списания и выдачи доступа в независимые async-события требует другой модели согласованности и компенсаций.
5. **Регистрация и уникальность email.** Вход и проверка занятости теперь нечувствительны к регистру; новые email нормализуются. В БД исторически остаётся регистрозависимый UNIQUE. Следующий шаг — найти старые коллизии и сделать `UNIQUE(lower(email))`, а конфликт параллельной регистрации переводить в 409 по конкретному ограничению. Сейчас редкая гонка регистрации может дать общий 500 с откатом, без дублирования нового нормализованного email.
6. **Внешнее размещение.** Явно выбрать нелокальный профиль, заменить известные локальные секреты, определить хранение сессии, HTTPS, ограничение частоты входа, восстановление доступа, резервное копирование и мониторинг. Наличие профиля `prod` в команде не выполняет эти действия автоматически.

Пошаговые учебные задания находятся в [PRACTICE.md](PRACTICE.md), объяснение внесённых решений — в [CHANGES_AND_THEORY.md](CHANGES_AND_THEORY.md).

## Проверка и данные

Тесты работают с `localhost:55432/lms_test`; перед очисткой проверяют адрес и имя БД. Тест принудительного сбоя доказывает откат после попытки списания и записи журнала. Конкурентные тесты удерживают блокировку в отдельном соединении и проверяют ожидающие запросы, а не полагаются только на удачное совпадение времени.

При первом ручном QA-запуске отдельного backend была допущена ошибка конфигурации: Maven-профиль тестовой БД приняли за переключение runtime. Этот запуск успел подключиться к основной БД, применить предусмотренную V8 и создать недостающие нулевые кошельки локальных демоаккаунтов admin/teacher. Его остановили. Проверка основной БД подтвердила баланс ученика `300.00` и четыре прежние покупки. Последующий браузерный сценарий выполнен с явно заданным адресом отдельной тестовой БД.

V8 уже применена к основной БД и должна оставаться неизменной. Не удалять её строку из истории Flyway. V1–V7 сохранены побайтно. Копия исходников до автоматических правок хранится в рабочем каталоге проверки; после обновления исходников приложение нужно перезапустить с `clean`.
