# Важные задачи для самостоятельной работы

Основной сценарий уже исправлен. Эти задачи оставлены для понимания бизнес-правил и устройства защиты данных. Выполнять по одной, после каждого изменения запускать подходящие тесты. Все эксперименты с ограничениями и очисткой данных делать в `lms_test` на порту 55432.

## 1. Регистронезависимая уникальность email и гонка регистрации

**Зачем.** Проверка `existsByEmailIgnoreCase` удобна для сообщения об ошибке, но два запроса могут пройти её одновременно. Кроме того, старый `UNIQUE(email)` разрешает исторические значения, отличающиеся регистром. Это хороший пример того, почему проверка сервиса не заменяет ограничение БД.

Шаги:

1. Прочитать `AuthService.register`, `UserRepository` и V1. Найти, где нормализуется email и где проверяется занятость.
2. Выполнить только чтение: `SELECT lower(email), count(*) FROM users GROUP BY lower(email) HAVING count(*) > 1;`. Наличие строк требует сначала решить, как объединять/переименовывать аккаунты; не удалять их автоматически.
3. Добавить **новую V9**, не менять V1 или уже применённую V8. Создать уникальный индекс по `lower(email)` после проверки коллизий. Имя ограничения/индекса выбрать явное и стабильное.
4. Обеспечить ранний SQL при сохранении пользователя, чтобы ожидаемый конфликт можно было обработать в нужном месте. Разобрать различие `save`, `saveAndFlush` и commit.
5. Только нарушение email-уникальности переводить в `ConflictException`. Прочие ошибки SQL должны сохранять серверный статус и логирование. Не ловить все исключения одной веткой «email занят».
6. Добавить интеграционный тест двух одновременных регистраций одного адреса. Ждать завершения обработки события кошелька, прежде чем считать его строки.

**Готово, когда:** один запрос успешен, другой получает 409; в БД один новый пользователь и один кошелёк; повтор с другим регистром тоже 409; неудачный запрос не оставляет лишних данных. Существующий аккаунт с смешанным регистром по-прежнему входит.

## 2. Решить судьбу оплаченного архивного курса

**Зачем.** Это правило продукта. Сейчас все непубличные курсы скрыты от ученика, даже с ACTIVE enrollment. Интерфейса архивации ещё нет. До его добавления нужно определить обещание покупателю.

1. Выбрать: архив скрывает только новые продажи или также закрывает уже купленное обучение.
2. Записать решение и отдельно определить поведение DRAFT. Правило архива не должно случайно открыть чужие черновики.
3. Найти проверки статуса в карточке курса, покупке и `LearningQueryService.requireAccess`. Изменить их согласованно.
4. Добавить тесты: каталог без токена; карточка и урок для покупателя; тот же урок без покупки; автор; попытка новой покупки.

**Готово, когда:** все пять случаев соответствуют выбранному правилу; архивация не создаёт новых списаний и не уничтожает исторический прогресс.

## 3. Сделать связь списания и покупки явной

**Зачем.** Сейчас UUID курса хранится в человекочитаемом описании `transactions`. Строить возврат или отчёт на разборе строки ненадёжно.

1. Нарисовать модель покупки: какую сущность обозначает операция, как связаны enrollment, курс и списание.
2. Выбрать структурированную связь: отдельный purchase ID/таблица либо другая явно обоснованная модель. Учесть бесплатный курс без денежного списания.
3. Описать миграцию старых данных. Не считать отсутствие старого журнала доказательством бесплатной покупки: часть тестовых балансов менялась вручную.
4. Добавить связь в той же транзакции, что списание и доступ, и проверить откат/конкуренцию существующими тестами.

**Готово, когда:** платную покупку и её списание можно однозначно найти по ID без чтения description; повтор запроса не создаёт вторую операцию. Реальный возврат денег — отдельная следующая задача.
